# board-documentation Specification

## Purpose
Defines the repository's documentation: `docs/wiki/` as the source of the GitHub wiki, its page taxonomy, pages generated from manifests and the board registry, the hardware acceptance vocabulary, the shared glossary, and the exclusion of private identifiers.
## Requirements
### Requirement: Wiki source in the repository
`docs/wiki/` SHALL be the source of the GitHub wiki, and CI SHALL mirror it after changes reach the default branch. Wiki links between pages SHALL use page names and SHALL be checked.

#### Scenario: Broken page link
- **WHEN** a page links to a wiki page that does not exist in `docs/wiki/`
- **THEN** `checks.wiki-links` fails

### Requirement: Page taxonomy
Wiki pages SHALL use a flat namespace: `Home`, `_Sidebar`, `Glossary`, `Guide-*`, `SoC-*`, `Research-*`, and for each board `<Board>`, `<Board>-Hardware-Matrix`, `<Board>-Boot-and-Recovery`, `<Board>-Firmware` and `<Board>-Free-vs-NonFree`.

#### Scenario: New board documentation
- **WHEN** a board is added
- **THEN** its five board pages exist and are linked from the sidebar

### Requirement: Generated pages
Hardware matrices, firmware tables and free-versus-non-free gap tables SHALL be generated by `nix build .#docs` from manifests, board options and fixtures. A check SHALL fail when committed generated pages differ from the generated output.

#### Scenario: Manifest change without regenerated docs
- **WHEN** a manifest entry changes and the docs are not regenerated
- **THEN** the docs check fails and names the command that regenerates them

### Requirement: Acceptance vocabulary
Hardware status SHALL use exactly: `verified` (with linked evidence), `implemented-unverified`, `blocked: <impediment>` and `pending`. Board pages SHALL state which hardware the maintainers have.

#### Scenario: Feature builds but is untested
- **WHEN** a feature evaluates and builds but has not been observed on hardware
- **THEN** its status is `implemented-unverified`

### Requirement: Shared glossary
`docs/wiki/Glossary.md` SHALL define the shared hardware terms, and documentation SHALL use them. Where another repository uses a different name for a defined term, the glossary SHALL list it.

#### Scenario: Term used in a new page
- **WHEN** a page describes a 40-pin header board
- **THEN** it calls the board an add-on of kind `hat`, as defined in the glossary

### Requirement: No private identifiers
Documentation MUST NOT contain private hostnames, addresses, serial numbers or other identifiers of the maintainers' machines.

#### Scenario: Copying bring-up notes
- **WHEN** research notes are moved into a `Research-*` page
- **THEN** machine identifiers are removed or replaced with neutral placeholders
